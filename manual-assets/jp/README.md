# Japanese set-asset manual intake

You are the reviewer. This folder is where you drop the correct
Japanese-market logo and symbol image files for each of the 127
Japanese Pokemon TCG sets. Nothing here ever uploads on its own.

## What you do

1. **Regenerate the folder structure** whenever the set list changes:
   ```
   npm run scaffold:jp-manual-assets
   ```
   This is safe to run again at any time. Anything you have already
   typed into `asset-index.csv` or `asset-index.json` stays.

2. **Find a set** in `asset-index.csv`. Open it in Excel, Numbers or
   VS Code — either works. Each row shows the exact `set_name`, the
   visible name, and the `asset_key` folder to open.

3. **Open that set's folder** under `inbox/<asset-key>/`. If the
   folder is missing, run the scaffold once more.

4. **Save the Japanese set logo** in that folder as `logo.png`,
   `logo.webp` or `logo.svg` — whichever matches the actual file
   type of the artwork you sourced.

5. **Save the Japanese set symbol** in that folder as `symbol.png`,
   `symbol.webp` or `symbol.svg`.

6. **Never rename a file to change its type.** If the file is
   actually a WebP but you rename it to `.png`, the audit will
   detect the mismatch and reject it. Keep the real extension.

7. **Prefer PNG, WebP or SVG.** JPEG is accepted but flagged as a
   warning because logos and symbols normally need a transparent
   background. Only fall back to JPEG when nothing else is
   available.

8. **Never use booster-pack photos, card scans, or English-market
   logos.** Those are the wrong artwork. If a set does not have a
   standalone logo (some Carddass / vending / McDonald's products
   never did), leave the folder empty — that is a valid outcome.

9. **Record the source URL** whenever you can. Open
   `asset-index.csv`, find the row for the set, and fill in
   `logo_source_url` and `symbol_source_url` with the direct link
   to the official product page or archive page you took the file
   from. This is provenance information — it is not itself proof
   of permission to reuse the artwork.

10. **One file per type per set.** Do not put `logo.png` and
    `logo.webp` in the same folder — the audit will refuse to
    guess. Pick the best one.

11. **After a batch of updates, run the audit:**
    ```
    npm run audit:jp-manual-assets
    ```
    Open the report it prints (`reports/jp-manual-set-assets-review.html`)
    in a browser. Errors need fixing; warnings are informational.

## What ships to production

- **Never**: the binary files you drop under `inbox/`. They are
  Git-ignored on purpose.
- **Always**: `asset-index.csv`, `asset-index.json`, this README, and
  the audit HTML/JSON when you choose to keep it.

A later block handles uploading approved files to Supabase Storage
and updating `set_metadata`. Nothing you do here changes the live
site.

## Folder shape

```

├── README.md            ← this file
├── asset-index.csv      ← the row-per-set spreadsheet (edit source URLs / notes here)
├── asset-index.json     ← the same data, JSON shape (edit source URLs / notes here)
└── inbox/               ← Git-ignored; regenerated by the scaffold
    ├── battle-partners/
    │   ├── logo.png     ← you save the real Japanese logo here
    │   └── symbol.png   ← you save the real Japanese symbol here
    ├── old-maid/
    ├── wild-force-and-cyber-judge/
    └── ...              ← one folder per set, 127 total
```

## Allowed filenames

| Kind   | Basename | Allowed extensions |
|--------|----------|--------------------|
| Logo   | `logo`   | `.png` `.webp` `.svg` `.jpg` `.jpeg` |
| Symbol | `symbol` | `.png` `.webp` `.svg` `.jpg` `.jpeg` |

The basename is **case sensitive**. `LOGO.png` will be rejected as
an unexpected file. Only one logo and only one symbol per set.

## Rule for future import code (authoritative)

The manual intake staging area is governed by four fixed rules. Any
future importer, storage uploader, or database sync tool that touches
these files must obey them without exception.

1. **`asset-index.json` is the authoritative mapping** between each
   Japanese set (`set_name`) and its manual asset folder (`asset_key`,
   `relative_folder`). It is the single source of truth. Nothing else
   in the repository — not filenames, not the scaffold script, not any
   downstream importer — may override it.

2. **Future import code must use the stored `asset_key` from the
   index.** When walking the intake to publish assets, always look up
   `asset_key` and `relative_folder` from the index entry keyed by
   `set_name`. Do not construct a folder path from the visible name.

3. **Future import code must not independently regenerate the folder
   key from a display name.** The slugify helper in
   `src/lib/set-assets/assetKey.ts` exists only for the scaffold's
   first-time key derivation and its collision guard. Downstream tools
   must never call it to invent a path for an existing set.

4. **The scaffold may regenerate and merge the index, but existing
   mappings and human-entered provenance must not be silently
   discarded.** The six durable fields — `logo_source_url`,
   `symbol_source_url`, `notes`, `approved`, `logo_content_hash`,
   `symbol_content_hash` — carry review effort forward across runs
   and are the reason the index cannot be treated as regenerable
   throwaway output.

## Quick commands

```bash
# Regenerate folders + refresh the index (keeps your source URLs / notes)
npm run scaffold:jp-manual-assets

# Audit whatever you have dropped so far — no uploads, no writes
npm run audit:jp-manual-assets
```
